# pic-helper 图片提示卡工作流

## 目标

把一张地点提示卡拆成两个可独立核验的部分：

1. 上半部：优先使用 Wikipedia/Wikimedia 图片作为唯一参考图，再做一次图生图风格化重绘；只有 Wikipedia 没有可用图时，才用 Google Images 补充参考图，并记录图片原始来源。
2. 下半部：以事实核查稿为唯一内容来源，使用确定性排版生成文字区。
3. 最后合成竖屏卡片，并分别检查建筑真实性、文字准确性和图片授权。

整卡不再依赖一次文生图同时完成建筑、中文文字和版式。图像模型不负责生成事实文字；文字排版器不负责猜测建筑外观。

## Kami 项目级排版集成

### 定位

Kami 作为本项目的排版、渲染和检查层，不替代上半部的真实参考图、图生图模型或图片生成提示词。安装位置为项目内的 `.agents/skills/kami/`，由 `skills-lock.json` 锁定来源和版本，不安装到全局 Agent 环境。

原始图片生成链路保持不变：真实建筑参考图仍然约束建筑形态，图片模型仍然只负责上半部的风格化重绘。Kami 不会自动调用图片生成模型，也不会修改已有的 v3、v4、v5 图片或生成提示词。

### 推荐职责分工

```text
核查.md + 提词卡初稿.md
          ↓
结构化内容与事实覆盖检查
          ↓
Kami HTML/CSS 排版
  ├── 已验收的上半部建筑图
  ├── 四个讲解模块
  └── SVG 时间轴
          ↓
渲染、截图检查、输出手机竖屏 PNG
```

Kami 的一页纸模板、内容结构检查、字体检查和视觉截图检查可以作为后续地点的公共能力。当前 v5 的 SVG + PNG 保留为基准版本，第一次 Kami 实验必须并行输出，不直接替换 v5。

### 当前可执行链路

每个新地点最多只做一次图片生成调用，后续全部确定性执行：

```text
Wikipedia/Wikimedia 图片
  → 有可用图片：直接作为 Codex 图生图唯一参考图
  → 没有可用图片：OpenCLI Google Images/Google Search 选择真实参考图和事实来源并记录
  → Codex 图生图（只生成上半部，保存最终 Prompt）
  → SVG 编排标题、四区提词和时间轴
  → scripts/render_card_png.py 调用项目内 Kami 渲染
  → 最终PNG/地点-vN.png
```

`scripts/render_card_png.py` 接收地点目录中的完整 SVG，临时生成 Kami HTML/PDF，中间文件自动清理，只把 PNG 写入根目录的 `最终PNG/`。因此每个地点目录可以保留真实参考图、上半部图生图、SVG、核查稿和 Prompt，而最终交付物集中在一个 PNG 文件夹中。Kami 只负责排版渲染，不会再次调用图像模型。

若 OpenCLI 图片检索遇到 CAPTCHA、同意页或浏览器拦截，立即暂停批量并在 `kanban.md` 记录恢复位置；不得静默改用原始网络抓取，也不得在没有真实参考图的情况下调用图生图。

### 本项目颜色和字体覆盖

Kami 默认的暖纸色 `#f5f4ed` 偏黄，不作为本项目默认值。用户已经指出当前卡片仍有轻微偏黄，因此后续 Kami 试验先使用更中性的暖白纸张 `#FCFBF7`，蓝色继续使用冷钴蓝 `#0B4FAF`。这只是下一轮排版试验的颜色候选，不回写已经生成的图片。

中文字体继续优先使用 Noto CJK。Kami 文档中提到的 TsangerJinKai02 存在个人使用限制，不作为本项目默认字体。

### Kami 试验验收门槛

使用英文楚报馆旧址作为第一张试验卡，沿用已经验收的上半部建筑图，不重新消耗图片生成额度。只有同时满足以下条件，才考虑把 Kami 作为后续地点的正式底座：

- 输出尺寸稳定为 `2520 × 5472`，并保持当前手机竖屏比例；
- 本地建筑 PNG、中文字体和内嵌 SVG 时间轴均能稳定渲染；
- 颜色不回到土黄，纸张负空间和钴蓝线条保持当前视觉方向；
- 正文在手机实际查看尺寸下可读，文字不溢出、不被压缩成注释大小；
- 每条卡片事实仍能回指 `核查.md`，并通过项目自己的建筑、文字和来源验收。

如果 Kami 的 PDF 中转或固定模板无法稳定满足精确手机长图要求，继续使用当前 SVG + Pillow 合成方案；Kami 仍可只用于内容结构和排版检查。

## 目录约定

每个地点目录保留以下材料：

- `参考图片/`：真实参考图、来源和许可证记录；
- `核查.md`：地点事实和证据边界；
- `提词卡初稿.md`：现场讲解内容；
- `生成提示词.md`：每次图像生成的输入、版本和结果说明；
- `地点-vN.png`：合成后的版本化成品或测试图。

参考图文件必须同时有来源说明，至少记录原始 URL、作者、许可证（若有）、抓取日期、原始尺寸和使用范围。Google 图片结果页只用于发现候选，不作为图片来源证明；事实优先采用政府、机构、报刊或其他可核验页面。

## 标准流程

### 1. 找到并确认真实参考图

先打开对应的 Wikipedia 条目和 Wikimedia Commons 文件。若有能确认主体、视角和授权的图片，直接选一张作为图生图参考。若 Wikipedia 没有对应条目或没有可用图片，再用地点名称、地址和建筑别名搜索 Google Images/Google Search，保留 5—10 个候选后去重，并为事实和图片分别记录原始来源。

候选排序按以下条件，而不是按搜索排名：

- 能确认是目标建筑；
- 能看到完整体量、转角、屋顶和主要立面；
- 视角适合重绘；
- 分辨率足够；
- 没有水印或严重遮挡；
- 有明确的开放许可证，优先 Public Domain、CC0 或 Wikimedia Commons 的明确授权。

如果两张图是同一建筑、角度和信息量相近，只保留一张，并在来源说明中记录被舍弃的重复结果。

### 2. 只对上半部做图生图

Wikipedia/Wikimedia 图片或 Google Images 兜底图片负责约束建筑身份和几何形态，Prompt 只描述希望保留或改变的媒介风格。无论参考图来自哪条分支，每个地点最多调用一次图生图。

建筑核验至少包括：

- 楼层数量；
- 正面与侧面的比例；
- 是否为转角建筑；
- 屋顶线和栏杆；
- 阳台、窗组、入口和台基的位置；
- 街道视角和主要遮挡关系。

图生图 Prompt 必须明确“保留参考图的建筑轮廓和视角”。禁止新增与参考图冲突的中央门廊、成排巨柱、穹顶、尖塔、旗帜和不存在的招牌。

输出的上半部不得包含标题、段落、日期或伪中文。文字统一留给下一个步骤。

### 3. 由事实稿生成下半部

下半部内容只允许来自 `核查.md` 和 `提词卡初稿.md`。模型可以帮助压缩和分组，但不能补写未经核查的日期、建筑细节或开放状态。

四区标题的默认顺序固定为：`建筑风格`、`它是什么地方`、`它经历了什么`、`现状`。后续新卡第一栏统一使用“建筑风格”；本规则不回改已经完成的第 34 号 dogfood 成图。

推荐使用 Markdown、HTML、SVG 或其他确定性渲染方式生成文字区，至少检查：

- 标题、编号和地址无错字；
- 每个事实能回指核查稿；
- 手机尺寸下正文可读；
- 长文本不会溢出或被压成微型字；
- AI 生成建筑图不会被误认为历史照片。

时间轴不再只放三个简单节点。若对应 Wikipedia 或一手资料存在明确沿革，默认提取 4–6 个年份/事件节点；若没有对应条目，则保留可核验的官方节点，并明确资料不足，不用推测补齐。

### 4. 合成与验收

成品保持版本化命名，例如 `地点-v3.png`。不要覆盖旧版本。

验收分三层：

1. 建筑层：与参考图并排检查，不得出现结构性幻觉。
2. 文本层：逐段对照核查稿，确认事实、字形和换行。
3. 来源层：保留参考图授权和署名信息；对 CC BY-SA 图片，发布时按许可证要求署名并处理衍生作品义务。

AI 重绘和参考图授权信息记录在项目文档中，不默认放进现场卡片。卡片优先服务导游扫读，不放来源提示或会分散注意力的解释性尾注。除非使用的是经过授权且未经改变的历史或现场照片，否则项目文档和发布说明中不能称为历史照片。
